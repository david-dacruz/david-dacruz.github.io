Field note 01 / AI operations

What breaks when an AI workflow reaches production

The model is rarely the whole problem. Production failures usually appear in the handoffs around it: incomplete inputs, unowned exceptions, invisible changes, and no safe way back.

David Dacruz9 August 20267 minute read

On this page

Start with the operator, not the prompt

A workflow becomes operational when someone owns its decisions. That person needs to know what the system may do, what requires review, which failure states matter, and when the workflow should stop.

Before choosing another model or rewriting a prompt, write down the accountable owner, the user affected by each output, and the action that output can trigger. This exposes risk faster than an abstract architecture diagram.

A useful test: if a wrong output appears on Friday evening, who can detect it, contain it, explain it, and repair the affected record?

Control the inputs and boundaries

Production inputs are inconsistent. Fields are missing, attachments change format, source systems disagree, and users paste material the original demo never encountered.

  • Validate required fields before the model runs.
  • Keep source identifiers with the generated result.
  • Define size, file-type, language, and freshness limits.
  • Reject or queue work that falls outside those limits.

Keep enough evidence to review a result

A useful audit trail connects an output to its source material, instructions, model version, tools, timestamps, reviewer, and downstream action. Without that chain, teams debate what probably happened instead of examining what happened.

This matters beyond debugging. Evidence is also how a human reviewer decides whether an output is trustworthy enough to use.

Design exceptions as part of the product

Human review should not be a vague safety label. Specify what enters review, what the reviewer sees, which actions are available, and how corrected decisions improve later runs.

Common queues include low-confidence extraction, conflicting source records, requests involving sensitive data, tool failures, and outputs that could create an external commitment.

Release deliberately

  1. Replay a representative test set.
  2. Run in shadow mode without taking external action.
  3. Compare output with the current manual process.
  4. Release to a small group with observable limits.
  5. Keep rollback and manual fallback available.
